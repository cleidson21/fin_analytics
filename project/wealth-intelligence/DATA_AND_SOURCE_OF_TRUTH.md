**Status:** VERIFIED (current sources) + APPROVED (Phase 10.3 input boundaries)
**Date:** 2026-09-16

## Principle

The system enforces strict separation between:
- **USER GOVERNED DATA** — entered or confirmed by the user
- **EXTERNAL DATA** — retrieved from external services
- **DETERMINISTIC CALCULATIONS** — computed by the backend from verified inputs
- **AI INTERPRETATION** — generated by LLM, never authoritative

The LLM is **READ-ONLY** with respect to financial truth.

## Data Authority Rules

### USER GOVERNED DATA (never overwritten by system)
- Transaction ledger (immutable, append-only)
- Category corrections (append-only event log)
- Account definitions
- Goals (user creates/edits)
- is_manual=1 positions (protected from MyProfit overwrite)

### EXTERNAL DATA (always labeled as external, never presented as fact)
- yfinance quotes and history
- yfinance fundamentals
- MyProfit imported positions and returns
- Pierre Finance imported transactions
- Future: news, analyst consensus, BCB macro data

### DETERMINISTIC CALCULATIONS (authoritative, computed by backend)
- Portfolio value = Σ(position_quantity × current_price)
- Portfolio return = from portfolio_snapshots (MyProfit-sourced pct data)
- Dividend yield = gross_amount / avg_cost
- Goal progress = current_amount / target_amount
- Retirement projection = compound interest formula with user assumptions
- Savings rate = (income - expenses) / income
- Portfolio allocation = per-class value / total portfolio value
- Spending averages, category breakdowns, and approved historical trends; rolling averages require a separate future contract

### AI INTERPRETATION (never authoritative, always labeled)
- "Your spending pattern suggests..."
- "The portfolio movement may be explained by..."
- "Current market conditions relevant to your holdings include..."
- "Based on your goals and current trajectory..."

## Financial Health Data Semantics (Lote 10.2)

### 1. Data Authority
* **RAW Data**: As brought by `TransactionRepository.upsert()`. `amount` is stored exactly as received.
* **Governance State**: Regulated via `governance_status` and `economic_classification`.
* **CLASSIFIED**: Only transactions with `governance_status = 'CLASSIFIED'` are considered certified financial facts.
* **PENDING**: Transactions yet to be classified. Excluded from all financial health aggregations (except for a possible warning count).
* **ENTRADA**: Governed transactions classified as Income. Included in Total Income (`sum(abs(amount))`).
* **SAIDA**: Governed transactions classified as Expense. Included in Total Expenses (`sum(abs(amount))`).
* **IGNORAR**: Ignored transactions. Strictly excluded from all cashflow and anomaly metrics.
* **Transaction Date**: The authoritative period is the RAW API date (`transactions.date`), NOT the `governed_at` timestamp.
* **Amount Semantics**: Always calculated as `abs(amount)` to prevent signal collision (e.g., negative expense).
* **Consolidated Account Scope**: Financial Health aggregates all eligible governed transactions across accounts and providers in the local single-tenant database. It does not filter by `account_provider`, `account_external_id`, or account identifier in this phase (ADR-017).
* **Live Health Outputs**: Financial Health is read-only and calculated from the current `CLASSIFIED` ledger at request time. A legitimate later governance decision changes future Health responses automatically; no snapshot, reimport, migration, rebuild, or cache invalidation is required.
* **Certified Read Layer**: `HealthFinancialQuery` is the single source of truth for downstream Financial Health services.

### 2. Temporal Semantics
* **Closed Month**: A fully completed calendar month (e.g., September is closed on October 1st).
* **Current/In-Progress Month**: The ongoing calendar month. Aggregations here represent a partial *run-rate*.
* **Baseline Period**: The historical closed months used for comparison. The operational baseline currently uses the three continuous closed months immediately preceding the analysed month; the current month is *never* part of the baseline. The horizon may evolve in a future phase without changing the data contract.
* **Minimum Historical Data**: The minimum occurrences required by future historical and anomaly metrics remain part of their own phase contracts; it does not change the operational three-month baseline defined here.
* **Boundary Behavior**: A query for "2026-09" uses the half-open interval `[2026-09-01 00:00:00, 2026-10-01 00:00:00)`.

### 4. Cashflow Metrics Contract (10.2.2)
* **Totals:** `total_income` and `total_expense` are the certified values supplied by `HealthFinancialQuery`.
* **Net cashflow and savings:** `net_cashflow = total_income - total_expense`; `savings_amount = net_cashflow`.
* **Savings rate:** `savings_rate = savings_amount / total_income`. When `total_income == 0`, the rate is `None` rather than an artificial zero.
* **Monthly averages:** income, expense, and monthly net cashflow are averaged only over supplied monthly totals. An empty collection yields `None` averages; missing months are never synthesized.
* **Precision:** `transactions.amount` is `NUMERIC(12,2)`. SQLite returns `SUM(ABS(amount))` as a binary `float`; `HealthFinancialQuery` therefore normalizes monetary aggregates once at its read boundary to `Decimal` quantized to `0.01`. Downstream calculations use those certified `Decimal` values without premature rounding. Savings rate remains an analytical `Decimal` fraction (`0.4` represents 40%) and is not quantized to cents.
* **Trend:** the deterministic month-over-month contract is locked by ADR-018, implemented by `FinancialTrendService` in 10.2.10-B, and independently validated on 2026-09-15 against the read-only certified SQLite ledger with a separate Python `Decimal` oracle.

### 5. Historical Financial Metrics Contract (10.2.3)
* **Input and authority:** `HistoricalFinancialMetricsService` receives only certified monthly totals supplied by `HealthFinancialQuery`; it does not access transactions, SQLite, RAW, or SQLAlchemy.
* **Series:** each `MonthlyFinancialMetricsDTO` uses the existing `YYYY-MM` `reference_month` convention and contains certified income, expense, net cashflow, savings amount, and savings rate. Records are returned in chronological ascending order.
* **Gaps and zeros:** only supplied months appear. Missing months remain absent and are never synthesized; an explicitly supplied zero-income/zero-expense month remains a real record. Empty input returns an empty series.
* **Duplicates:** duplicate `reference_month` input is rejected with `ValueError`; monthly input is expected to be pre-consolidated by the read layer.
* **Closed/current selection:** this layer does not infer baseline membership or complete current partial months. The caller selects the supplied months; the closed-month baseline remains separate.
* **Trend boundary:** ADR-018 supersedes the prior absence of a month-over-month contract. `FinancialTrendService` now compares only the exact required closed months without filling or skipping gaps. Rolling averages remain outside the locked acceptance contract.

---

### 6. Category Expense Intelligence Contract (10.2.4)
* **Input and authority:** `CategoryExpenseIntelligenceService` receives only pre-consolidated, certified category totals from `HealthFinancialQuery.get_category_expenses`. It does not access transactions, SQLite, RAW, Pierre, or SQLAlchemy.
* **Metrics:** `total_expense` is the exact sum of supplied `expense_total` values. Each category has `share_of_expenses = expense_total / total_expense`, or `None` when the supplied total is zero. Monetary values remain cent-scale `Decimal`; shares remain analytical `Decimal`.
* **Ranking:** output is sorted by expense descending and, for equal values, lexicographically by the received category label. Ranks are sequential. The first item is `top_category`; empty input has no top category.
* **Labels and duplicates:** labels are preserved exactly as received, including the repository fallback `Uncategorized`; no aliases, encoding fixes, or semantic grouping occur. Duplicate category input is rejected with `ValueError` because the read layer must already consolidate it.
* **Scope boundary:** ADR-018 exact month-over-month category trends are implemented in 10.2.10-B. Additional concentration measures, rolling history, normalization, and aliases remain outside this contract; anomalies remain governed independently by ADR-015.

### 7. Spending Anomaly Contract (10.2.5, ADR-015)
* **Global baseline:** the target month is evaluated only with its three immediately preceding continuous closed months. The target month is excluded; gaps are not synthesized. If those three months do not exist, the global state is `INSUFFICIENT_BASELINE` and no anomalies are produced.
* **Category presence:** a category is present in a month only when a certified record exists. Absence is not zero. An explicit `Decimal('0.00')` record is present, including for history counting and the arithmetic mean.
* **SPIKE eligibility and reference:** a current category needs presence in at least two of the three baseline months. Its `baseline_reference` is the arithmetic mean of certified values from months where it is present; absent months are not inserted as zero. The reference must be `>= Decimal('50.00')`.
* **SPIKE rule:** `SPIKE` when `current_expense > baseline_reference * Decimal('1.5')`. Equality at exactly 1.5x is `NORMAL`. A one-of-three history is `INSUFFICIENT_HISTORY`; an eligible category below the floor is `BELOW_BASELINE_FLOOR`.
* **NEW_EXPENSE rule:** a current category absent in all three baseline months is `NEW_EXPENSE` when `current_expense >= Decimal('100.00')`; otherwise it is `NEW_EXPENSE_BELOW_THRESHOLD`. An explicit historical zero prevents NEW_EXPENSE because the category is present.
* **States and anomalies:** valid states are `NORMAL`, `SPIKE`, `NEW_EXPENSE`, `INSUFFICIENT_HISTORY`, `BELOW_BASELINE_FLOOR`, `NEW_EXPENSE_BELOW_THRESHOLD`, and global `INSUFFICIENT_BASELINE`. Only `SPIKE` and `NEW_EXPENSE` belong in an anomalies collection.
* **Precision and matching:** money and thresholds use `Decimal`; ratio is unrounded analytical `Decimal` when baseline is positive, otherwise `None`. Categories match by the exact certified string: no trim, case, accent, encoding, alias, or semantic normalization occurs.
* **Explainability:** every future evaluation must retain category, state, current expense, historical values, baseline months used, baseline reference, ratio, ratio threshold, baseline floor, and NEW_EXPENSE threshold when applicable. No severity or AI narrative is part of the contract.

### 8. Financial Trend and Acceptance Boundary (10.2.10-A, ADR-018)
* **Authority:** ADR-018 is the complete executable contract. This document records only its data-boundary consequences.
* **Closed-month comparisons:** global and category trends compare two consecutive closed calendar months. A current partial requested month resolves to the latest closed target month; unavailable or non-consecutive data yields `INSUFFICIENT_DATA`. Gaps are never synthesized or skipped.
* **Facts:** global trends cover income, expense, net cashflow, and savings rate. Category trends preserve exact label identity, explicit-zero presence, and absence semantics. All values and deltas remain `Decimal`.
* **Savings semantics:** `savings_amount` is realized surplus/deficit and is not sustainable contribution capacity or investment capacity. Those capacities are deferred to Planning and Portfolio Intelligence.
* **Stability readiness:** the 16 continuous closed months make a simple deterministic stability-facts contract feasible, but no formula or composite score is approved yet.
* **Implemented boundary:** `FinancialTrendService` accepts already-certified monthly financial metrics and monthly category totals. It has no transaction, SQLite, RAW, Pierre, API, or UI access. Caller-supplied current-month identity keeps partial-month resolution deterministic and testable.
* **Category ordering:** target-present categories are emitted by current expense descending with lexical tie-break; disappeared categories follow, ordered by previous expense descending with lexical tie-break. Ordering is technical and creates no new rank or pressure score.
* **Exposure boundary:** 10.2.10-C implements authenticated read-only API/UI exposure of the validated facts. The endpoint serializes `Decimal` as JSON strings/null, passes the API-boundary current month explicitly to the engine, and never recalculates trend arithmetic. The UI labels closed-period context and formats savings-rate absolute deltas as percentage points only for presentation.
* **Deferred:** stability remains `NOT IMPLEMENTED — CONTRACT PENDING`.

## Planning Data Boundary (Phase 10.3 — CONTRACT LOCKED, ADR-019/020/021)

Planning will not create a second financial truth. Its inputs must retain source, scope, reference/as-of date, and Decimal precision.

| Planning Input | Source | Authority | Approved Use | Not Approved |
|---|---|---|---|---|
| Goal target/date/type/status | `goals` | User governed | Goal-specific planning facts | Duplicating Goal ownership in Planning |
| `GOAL_CURRENT_AMOUNT` | `goals.current_amount` | User governed | Explicit goal-specific initial-wealth origin | Treating it automatically as total wealth or adding it to another origin |
| `INVESTMENT_PORTFOLIO_SNAPSHOT` | Selected `portfolio_snapshots.patrimonio` | External → governed (MyProfit) | Explicit investment-wealth origin with account/scope/as-of provenance | Calling it consolidated net worth or summing positions again |
| `USER_PROVIDED_SCENARIO` | Explicit Planning request | User assumption | Explicit scenario initial-wealth origin | Presenting it as observed/certified wealth |
| Realized surplus/deficit | `HistoricalFinancialMetricsService` over certified Health facts | Deterministic historical fact | Context and future capacity-contract input | Equating it to sustainable contribution capacity |
| Goal planned contribution | `goals.monthly_contribution` | User governed | `goal_planned_monthly_contribution` only | Treating it as the scenario contribution without explicit user selection/copy |
| Scenario contribution | Explicit Planning request | User assumption | Non-negative `scenario_monthly_contribution` | Deriving it from Goal or Health automatically |
| Return rate | Explicit Planning request | Scenario assumption | Finite effective annual Decimal `> -1` | Inferring future return from portfolio history or market data |
| Inflation rate | Explicit Planning request | Scenario assumption | Finite effective annual Decimal `> -1`, only in the approved nominal-to-real mode | Treating historical IPCA as a future forecast or double-adjusting a real return |
| Target value basis | Explicit Planning request | User assumption | `NOMINAL` or `REAL` basis required for Goal Planning | Inferring basis from the existing Goal row |
| Portfolio history/benchmarks | `portfolio_snapshots` | External → governed historical fact | Context and independent reconciliation | Automatic projection assumptions |
| Dividends | `income_events` | External → governed historical fact | Historical context | Guaranteed future income or FIRE result |

### Required Read Boundary

- Existing Goals and Investments HTTP responses are not internal Planning data sources. Planning must consume repositories/read services directly.
- Goal persistence uses SQL `Numeric`, but the current Goal entity/repository/DTO path converts money to `float`. A Planning-specific Decimal-safe input boundary is required before calculations; this is not authorization to refactor Goals in advance.
- Existing Investments routes query snapshots directly and expose several float/dynamic-dictionary fields. Phase 10.3.1 must expose approved `portfolio_snapshots.patrimonio` facts through a typed read-only Decimal contract.
- `PortfolioSnapshotModel.patrimonio` represents the investment portfolio imported from MyProfit. It is not proven to be consolidated net worth across cash accounts, liabilities, real estate, non-imported accounts, or all asset sources; future API/UI must not label it `net worth`.
- Exactly one initial-wealth origin participates in a calculation. Planning never sums Goal progress, portfolio snapshots, position valuations, or user-provided scenario wealth automatically.
- Every input/result retains origin, scope/account where applicable, reference/as-of date, source/update timestamp when available, and Decimal precision. No silent fallback is approved.
- Health trends, categories, and anomalies can provide factual context but are not default numerical projection inputs.
- `realized_savings_amount`, `goal_planned_monthly_contribution`, `scenario_monthly_contribution`, and `sustainable_monthly_contribution_capacity` are distinct. No automatic conversion is permitted; sustainable capacity remains uncontracted and deferred to 10.3.7.
- Portfolio return history, CDI, IPCA, IBOV, dividend history, and Health trends are context only and never automatic future assumptions.

### Approved Deterministic Lineage

```text
Certified Wealth + Certified Health Facts + User-Governed Goals
                              + Explicit User Assumptions
                                      ↓
                         Decimal Planning Inputs
                                      ↓
                    Deterministic Planning Engines
                                      ↓
               Results + assumptions + provenance/as-of
                                      ↓
                              API → UI
                                      ↓
                    Future LLM interpretation only
```

No production Planning engine, result, API, persistence model, or UI exists yet. ADRs 019–022 are the detailed approved contracts; `IMPLEMENTATION_ROADMAP.md` owns execution status. Phase 10.3.1 is limited to the typed Decimal read foundation.

## Data Quality Notes

### MyProfit Data [VERIFIED]
- Positions: quantity + avg_price from MyProfit CSV exports
- Portfolio evolution: monthly snapshots with benchmark comparisons
- Income events: dividends, JCP, amortization
- **Limitation:** MyProfit is a third-party app. Data is as accurate as the user's MyProfit account. Manual reconciliation required for full trust.

### yfinance Data [VERIFIED]
- **Quote freshness:** 15-min in-memory cache (not market real-time)
- **History:** OHLCV, not adjusted for corporate actions in all cases
- **Fundamentals (yf.info):** Unreliable, especially for Brazilian FIIs and smaller stocks
- **FX:** BRL=X via Yahoo, 1-hour cache, fallback 5.0 hardcoded
- **FIXED_INCOME assets:** No yfinance ticker available — returns None

### Goals Data [VERIFIED FOUNDATION / PLANNING BOUNDARY APPROVED]
- `target_amount`, `target_date`, `current_amount`, `monthly_contribution`, `goal_type`, `status`, `priority`, `linked_account_id`, and `assumptions_json` exist after Phase 10.1.
- Goal values are user governed. `current_amount` is manual and nullable; it is not automatically linked to certified wealth.
- No projection engine exists yet. `assumptions_json` is opaque storage and is not an approved executable Planning contract or canonical scenario persistence.
- Goals does not define whether `target_amount` is future nominal money or current purchasing power. Goal Planning must receive an explicit `target_value_basis = NOMINAL | REAL` (or exactly equivalent approved field) without inferring or changing the Goal row.

## What AI May and May NOT Do [NON-NEGOTIABLE]

### AI MAY:
- Interpret verified financial data
- Summarize trends from calculated metrics
- Explain possible causes for observed patterns
- Present external analyst consensus (clearly labeled as external)
- Summarize retrieved news (traceable to source)
- Generate portfolio briefings from calculated data
- Identify anomalies in spending patterns
- Generate natural-language explanations of goal progress
- Present scenarios based on user-provided assumptions

### AI MAY NOT:
- Modify transactions, balances, positions, or portfolio values
- Generate financial data not derived from the verified pipeline
- Fabricate analyst consensus
- Invent price movements or reasons for them
- Perform financial arithmetic that replaces backend calculations
- Store interpretations as financial facts
- Present AI-generated text as objective financial data

If no reliable explanation is available, the system must state:
> "The available sources do not provide enough evidence to attribute this movement."
